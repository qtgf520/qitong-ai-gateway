## 一、当前诊断：qtai-sj 路由问题

### 现象
- 带前缀（綦小桐/qtai-sj/XiaoTong）→ 正常回复
- 不带前缀 → 走模型通道，但不回复，也没接到提交内容
- 单独选其他模型 → 正常

### 根因定位
前缀指令匹配和无前缀消息路由是两套逻辑。带前缀走了"指令通道"（解析→路由→执行），不带前缀走了"模型通道"但消息在通道中间被丢弃——可能是：

1. **无前缀消息没有默认目标模型**：`qtai-sj` 收到不带前缀的消息后，既没有命中指令也没有绑定默认模型，消息进入队列但无消费者
2. **前缀剥离后空内容**：无前缀时剥离逻辑返回空字符串或 null，请求体 body 为空被 Ktor 直接丢弃
3. **路由条件互斥不完整**：`if (hasPrefix) { ... } else { ... }` 的 else 分支缺少兜底策略

### 一键修复点

```
修复位置：GatewayDispatcher.kt / ModelRouter.kt（qtai-sj 的消息入口）
修复原则：无前缀消息 = 普通消息 → 走 qtai-sj 绑定的"脑子模型"或默认模型

改法（伪代码）：
if (message.hasPrefix("綦小桐")) {
    // 指令通道：解析指令 → 路由 → 执行
    handleCommand(message)
} else {
    // 普通消息通道：直接转发给 bindModel（绑定的脑子模型）
    // 如果没绑定 → 回退到最快可用模型
    val target = bindModel ?: ranking.firstOrNull()?.model
    if (target == null) {
        return error("无可用模型")  // ← 关键：必须有明确错误返回
    }
    forward(message, target)
}
```

检查清单：
- [ ] 无前缀消息是否有明确的目标模型？
- [ ] 剥离前缀的逻辑是否兼容无前缀输入（返回原消息而非 null）？
- [ ] 路由失败时是否有明确错误信息返回给客户端（而非静默丢弃）？

## 二、多模态支持（图片等）

### 当前
模型列表/能力标记已做（v3.6.6），但图片消息可能被拦截或剥离。

### 修复
```
位置：ModelAdapter.kt / RequestBuilder.kt
修复：构造请求时检查消息是否包含 image/vision 内容

改法：
1. 读取消息中的 image_url / base64 字段
2. 检查目标模型的能力标记 supportsVision
3. 不支持 → 自动切换到支持图片的最快模型（或返回错误）
4. 支持 → 按 OpenAI Vision 格式构造请求体
{
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text", "text": "描述这张图"},
      {"type": "image_url", "image_url": {"url": "data:image/..."}}
    ]
  }]
}
```

## 三、思考引导（think 注入）

### 綦桐的想法
让 qtai-sj 注入 `<think>` 标签引导 AI 深度思考。

### 原理
不是简单加 `<think>` 字符串——而是通过 system prompt 或第一个 assistant 消息引导模型进入思考模式。DeepSeek/Claude 等模型有原生的 thinking/reasoning 能力。

### 实现
```
位置：PromptBuilder.kt（新建）或 GatewayDispatcher.kt

改法：
1. 在用户消息前插入 system 消息：
   "请在回答之前，先在你的思考过程中分析以下要点：
    1) 用户的核心需求是什么
    2) 有哪些可能的解法
    3) 每种解法的优缺点
    4) 最终推荐及理由"

2. 可配置化：在 APP 设置中加"思考深度"滑块 → 控制 system prompt 的详细程度
   - 轻度：只加 "请先思考再回答"
   - 深度：加结构化思考模板
   - 关闭：不加任何引导

3. 对于支持原生 thinking 的模型（DeepSeek R1/Claude 4），直接用 API 参数而非注入 prompt
```

## 四、群聊模式（虚拟沙箱 + AI互聊 + 总结）

### 綦桐想法
5个 AI 在一个群聊区域同时对话 → 统一总结输出。要求可以**自由开关**。

### 免免的核心架构判断
群聊模式确实很简单——难的不是群聊本身，而是**把原生子代理包装成可用功能**。

免免提出的关键设计：
> "虚拟沙箱环境，将 AI 与其他 AI 接入该环境，AI 之间可以聊天探讨，最终再让第六个 AI 总结他们的。"

和笨重的"固定5个AI同时回答"不同——这个模式的核心是**AI之间可以互相对话，不是各说各的然后拼起来**。

### 实现（可自由开关）
```
位置：新建 GroupChatManager.kt（独立模块，可开关）

架构：
┌─────────────────────────────────┐
│           虚拟沙箱环境            │
│  ┌──────┐ ┌──────┐ ┌──────┐    │
│  │ AI-A │→│ AI-B │→│ AI-C │    │  ← AI 之间可以互相 @ 和回复
│  └──────┘ └──────┘ └──────┘    │
│       ↓ 对话记录 ↓               │
│  ┌──────────────────────────┐  │
│  │    第六个 AI（总结者）      │  │
│  └──────────────────────────┘  │
└─────────────────────────────────┘

改法（三步）：
1. 用户选择 N 个模型 + 1 个总结模型 → 开启群聊
2. 用户发消息 → 广播给第一个 AI
   → AI 回复后，下一条消息自动 @ 下一个 AI
   → 每个 AI 可以看到之前的对话记录
   → 可以互相引用、反驳、补充
3. 所有 AI 发言完毕 → 总结者读取全部聊天记录 → 输出整合结论

关键规则：
- 每个 AI 看到的是完整聊天记录（不是只看用户原始问题）
- AI 之间用 [@AI名称] 格式互相点名
- 可选"轮次限制"：N 轮后自动触发总结
- 开关：一键开启/关闭，关闭后恢复正常单模型模式
```

### 为什么这比"固定5个并行"更好
| 固定5个并行 | 虚拟沙箱互聊 |
|------------|------------|
| 各说各的，互不知情 | AI 互相引用、反驳、补充 |
| 输出拼在一起人工甄别 | 总结者给最终结论 |
| 质量取决于单个AI | 质量来自多轮对话碰撞 |
| 无法开启中途对话 | 随时可以 @ 任何 AI |

### 自由度
- 用户自定义：模型数量、轮次上限、总结者身份
- 可以只有2个AI互相辩论，也可以6个AI头脑风暴
- 开启/关闭按钮在首页，不影响正常使用

### 群聊 + 子代理：不冲突，分层共存

群聊和子代理不是二选一。它们是两层：

| 层 | 谁决策 | 模式 |
|----|--------|------|
| 上层：群聊 | 用户手动 | 用户选N个模型+1个总结者 → 虚拟沙箱互聊 |
| 下层：子代理 | AI自主 | AI分析问题 → 自己拆任务 → 自己分配 → 自己合并 |

群聊 = 子代理的一种**预设策略**。用户没有手动开群聊时，AI 仍然拥有子代理能力——遇到复杂问题自己拆解。用户开了群聊，就是手动接管了子代理的配置权。

实现上：
- 子代理先做（底层能力，改了 GatewayDispatcher 就能用）
- 群聊后做（UI层，选模型+开沙箱+展示聊天记录）
- 群聊调用的是同一个子代理接口

## 十一、AI 开发助手：工作记忆系统

### 问题
綦桐："AI 太笨了，每次都忘掉自己在干什么，改着改着就搞坏了。"

### 根因
提示词注入有上下文长度限制，项目越复杂越容易"失忆"。AI 需要的是**外部记忆文件**——不依赖提示词，每次唤醒先读。

### 方案：模仿 Skill 的自动记忆

不是给 AI 写"你是綦桐的助手"这种设定——而是给 AI 一套**可持久化的项目状态卡**。

### 记忆文件结构

```
文件位置：app/.operit/DEV_MEMORY.md

内容模板（AI 每次被唤醒先读这个文件）：

========================================
# 綦桐AI网关 · 开发状态卡
> 最后更新：2026-07-09 01:30
> 当前版本：v3.7.7 → 目标 v3.8

## 当前任务
[ ] 🔴 修复 qtai-sj 无前缀路由
[ ] 🔴 多模态支持（图片）
[ ] 🟡 思考引导可配置
[ ] 🟡 群聊模式（虚拟沙箱）
[ ] ⚪ LiteLLM 路由优化

## 当前正在做
> 修复 qtai-sj 无前缀路由
> 文件：GatewayDispatcher.kt 第 87 行
> 状态：已定位 else 分支缺兜底，待修改

## 已完成
[x] 已读取方案文件：綦桐AI网关_v3.8_改进方案.md

## 验证记录
| 时间 | 修改文件 | 编译 | 安装 | 测试结果 |
|------|---------|:--:|:--:|------|

| - | - | - | - | - |

## 规则

```

### 使用流程

```
用户唤醒 AI
    ↓
AI 第一步：读 DEV_MEMORY.md + 改进方案.md
    ↓
AI："我知道现在要修 qtai-sj 路由，上次改到 GatewayDispatcher.kt"
    ↓
改一段 → 编译 → 安装 → 测 → 标记
    ↓
更新 DEV_MEMORY.md："[x] qtai-sj 修复完成，下一步：多模态"
    ↓
下次唤醒：AI 读记忆，知道 qtai-sj 修完了，该做多模态了
```

### 为什么比提示词注入更好

| 提示词注入 | 工作记忆文件 |
|-----------|------------|
| 吃上下文窗口，项目大了记不住 | 独立文件，不占上下文 |
| 每次重新"你是綦桐的助手" | 每次读"上次干到哪了" |
| 无法跟踪进度 | 有完成清单和验证记录 |
| AI 自己乱改 | 有规则约束："改一个，验一个，记一个" |
